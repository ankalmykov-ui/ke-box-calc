# Архитектура KE | BOX CALC v2.0

Статус: архитектурная база этапа 1.
Источник: ТЗ v2.2 от 27.08.2026

## 1. Назначение

KE | BOX CALC v2.0 — самостоятельное веб-приложение для технологического и экономического расчёта заказов на гофроупаковку. Система должна выдавать не отдельный геометрический раскрой, а целостные технологически допустимые варианты изготовления.

Сквозной процесс:

`заказ → геометрия → ограничения → композиция → конкретное сырьё → раскрой → ECT/BCT → переработка → производительность → полная стоимость → выбор → списание → отчёт`

Если звено, обязательное для следующего шага, не подтверждено, система не изображает полный результат. Она возвращает явный статус неполноты и перечень недостающих данных.

## 2. Архитектурный стиль

На старте используется модульный монолит:

- PWA-клиент;
- FastAPI с версионируемым REST API `/api/v2`;
- чистое расчётное ядро Python без доступа к HTTP и базе;
- PostgreSQL как единственный источник оперативных данных;
- фоновые задачи только для импорта, PDF и других долгих операций;
- объектное хранилище для исходных файлов импорта и сформированных отчётов.

Микросервисы на первом этапе не вводятся. Границы модулей обязательны, чтобы позднее отделить тяжёлый оптимизатор или отчётный сервис без изменения предметной модели.

## 3. Модули

| Модуль | Ответственность | Не имеет права |
|---|---|---|
| Identity & Scope | пользователи, роли, организация, площадка, склад | выполнять расчёты и движения |
| Reference Data | профили, марки, нормы, оборудование, припуски, тарифы | менять историю задним числом |
| Materials | карточки сырья, роли, ширины, цены, внешние идентификаторы | хранить композиции внутри карточки сырья |
| Warehouse | партии, рулоны, поступления, остатки, инвентаризация, списание, сторно | произвольно перезаписывать остаток |
| Compositions | версии композиций, слои, допустимые материалы, стоимость и история | считать лабораторный BCT нормативом |
| Laboratory | фактические ECT/BCT, сопоставимость испытаний, статистика | молча объединять несопоставимые записи |
| Orders | заказы, позиции, состояния, исходные данные | изменять сохранённый snapshot расчёта |
| Calculation | геометрия, генерация и оценка вариантов, ранжирование | списывать сырьё и формировать PDF |
| Selection | выбор менеджера и причина отклонения | разрешать недопустимый вариант |
| Reporting | A4 «Экспресс», «Технологу», схемы раскроя | создавать складские движения |
| Audit | неизменяемый журнал критичных действий | содержать бизнес-логику других модулей |

## 4. Главный агрегат расчёта

Центральная сущность — `CalculationVariant`. Она создаётся и оценивается как единое целое. Вариант включает:

- позиции и производственные количества;
- композицию и конкретное сырьё каждого слоя;
- партии/рулоны и фактические ширины;
- ширину полотна, ручьи, ярусы и длины реза;
- технологический припуск по длине;
- все виды отходов без двойного учёта;
- ECT, расчётный BCT и сопоставимый фактический BCT;
- маршрут переработки, скорость, время и переналадки;
- расход в массе, площади и погонных метрах;
- стоимость 1 м², заготовки, позиции, запуска и заказа;
- версии всех формул и справочников;
- статус допустимости и объяснение решения.

Геометрический раскрой без композиции и цены может быть диагностическим кандидатом, но не называется экономически оптимальным вариантом.

## 5. Расчётный конвейер

1. Нормализовать вход и закрепить канонические оси MD/CD.
2. Рассчитать чистовую геометрию без технологического отхода.
3. Провести раннюю блокирующую проверку гофроагрегата и переработки.
4. Получить кандидаты композиций из фактического сырья. Марка из заказа остаётся
   справочным требованием, но не является жёстким фильтром: допустимость определяет BCT.
5. Подобрать конкретное доступное сырьё по слоям, ширинам, партиям и рулонам.
6. Сгенерировать размещения по ширине, припуски по длине и назначения двух ярусов.
7. Проверить требуемый BCT, прогноз BCT по сопоставимым лабораторным испытаниям,
   склад, оборудование и технологическую совместимость.
8. Рассчитать материальный баланс, производительность и полную стоимость.
9. Исключить недопустимые варианты.
10. Детерминированно ранжировать допустимые варианты.
11. Сохранить snapshot полного набора входов, версий, кандидатов и причин исключения.

## 6. Состояния

### Заказ

`draft → validated → calculated → variant_selected → writeoff_confirmed`

Дополнительные переходы:

- `draft|validated|calculated|variant_selected → cancelled`;
- `writeoff_confirmed → writeoff_reversed` только через сторно;
- очистка интерфейса не удаляет сохранённые сущности.

### Вариант

- `blocked` — нарушено обязательное ограничение;
- `feasible_incomplete` — технологически возможен, но нет полной цены или подтверждённой прочности;
- `feasible_priced` — допустим и имеет сопоставимую полную стоимость;
- `recommended` — первый по алгоритмическому рейтингу среди `feasible_priced`;
- `selected` — выбран менеджером; метка не заменяет `recommended`.

Если нет ни одного `feasible_priced`, система не назначает экономически рекомендованный вариант.

## 7. Транзакционные границы

- Расчёт читает согласованный снимок данных, но не меняет склад.
- Выбор варианта сохраняется отдельно от расчётной рекомендации.
- Подтверждение списания — отдельная идемпотентная транзакция с повторной проверкой остатков и версий.
- PDF читает сохранённый snapshot и состояние списания, но ничего не резервирует и не списывает.
- Сторно создаёт обратные движения; исходные движения не редактируются.

## 8. Версионирование

Каждый расчёт хранит:

- `api_version`;
- `schema_version`;
- `calculation_engine_version`;
- версии геометрии, BCT, ранжирования и стоимостной модели;
- идентификаторы и версии применённых справочников;
- точные значения цен и остатков на момент расчёта.

Изменение текущего справочника не меняет старый результат.

## 9. Развёртывание

- `main` остаётся production v0.7.1 до отдельного решения;
- `v2-dev` создаёт только v2 preview/staging;
- staging и production имеют разные базы и секреты;
- preview не получает production `DATABASE_URL`;
- миграции проходят staging, автоматические тесты и проверку отката;
- деплой считается успешным только после проверки UI → API → база → ответ.

## 10. Политика переноса старых наработок

Наследуются знания и контрольные примеры, а не архитектура.

Допускается повторная реализация:

- геометрии FEFCO 0201 после прохождения эталона техкарты № 990;
- складских инвариантов идемпотентности, блокировок и неизменяемых движений;
- проверенных параметров оборудования;
- безопасного preview импортов.

Не переносятся как основа:

- последовательность «сначала раскрой, потом композиция»;
- сессионное хранение заказа как единственная модель;
- ручные ширины, не связанные с конкретным сырьём;
- ранжирование только по геометрическим потерям;
- смешение готовых функций и экранов-заглушек.
