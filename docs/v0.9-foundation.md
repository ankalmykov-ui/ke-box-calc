# Архитектурное решение v0.9 — фундамент данных и склада

## Границы первого среза

Первый срез создаёт устойчивый контракт между текущим расчётным клиентом и будущими версиями приложения. Он не пытается сразу заменить весь интерфейс v0.8.

Реализовано:

1. версионируемый API `/api/v1`;
2. последовательные миграции `0001_v0_9_foundation`, `0002_v0_9_compositions` и `0003_v0_9_material_prices`;
3. организации, площадки и склады;
4. карточки сырья, внешние идентификаторы, ширины, партии и рулоны;
5. поступление, производный баланс, подтверждение списания и сторно;
6. идемпотентность документов и блокировка конкурентных складских операций;
7. аудит критичных складских действий;
8. отдельные версии композиций, история BCT и стоимости за м².
9. отдельная неизменяемая история закупочных цен сырья.

Следующие срезы:

1. import batch → preview → подтверждение поступления;
2. выгрузка и обратная загрузка инвентаризации;
3. сохранение расчёта, вариантов раскроя и потребности по слоям;
4. складской экран и диалог «Подтвердить списание сырья»;
5. аутентификация и проверка прав на уровне организации/склада.

## Инварианты

- 1С — только внешний источник файла инвентаризационной сверки.
- Внутренний UUID является главным идентификатором.
- Остаток не хранится перезаписываемым полем.
- Любое изменение остатка создаёт неизменяемое движение.
- PDF не создаёт складских документов.
- Повтор запроса с тем же ключом идемпотентности возвращает исходный документ.
- Списание блокирует позиции, повторно проверяет баланс и либо проводится целиком, либо не проводится вообще.
- После списания возврат оформляется сторно, а исходные движения сохраняются.
- Имена таблиц и API не содержат номер клиентской версии.
- Версия композиции неизменяема; новое сочетание слоёв создаёт следующую версию.
- Расчётный BCT, фактический BCT и стоимость/м² хранятся отдельными временными рядами.

## Окружения

`v0.9-dev` разворачивается как отдельный preview. Его `DATABASE_URL` должен указывать только на staging-базу. Production v0.7.1 и `main` не получают новые переменные и миграции до отдельного решения о выпуске.

Для preview разрешён флаг `AUTO_APPLY_MIGRATIONS=1`. На холодном старте функция
применяет только ещё не зарегистрированные миграции; транзакционная advisory-lock
защищает от параллельного запуска нескольких serverless-инстансов. В production
флаг отсутствует.
