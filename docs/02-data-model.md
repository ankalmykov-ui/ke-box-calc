# Каноническая модель данных v2.0

## 1. Общие правила

- Все основные сущности имеют UUID.
- Каждая предметная запись ограничена организацией, а где требуется — площадкой и складом.
- Физические величины хранятся как `numeric`, а не `float`.
- Единица измерения указывается явно; преобразования версионируются.
- Исторические значения не перезаписываются: используется период действия или новая версия.
- Складской баланс вычисляется из движений.
- Денежные суммы хранят валюту, дату действия и источник.
- Время хранится в UTC, отображается в часовом поясе площадки.
- Ссылки на внешние системы не заменяют внутренний UUID.
- JSON допустим для snapshot и доказательств, но не вместо ключевых связей и ограничений.

## 2. Организация и права

| Таблица | Назначение |
|---|---|
| `organizations` | владелец данных |
| `sites` | производственные площадки |
| `warehouses` | склады площадки |
| `users` | пользователи |
| `roles` | менеджер, технолог, склад, администратор |
| `user_role_scopes` | права в пределах организации/площадки/склада |

Проверка прав выполняется backend для каждого изменения. Значение `created_by` из клиентского JSON не считается аутентификацией.

## 3. Сырьё

| Таблица | Ключевые данные |
|---|---|
| `materials` | карточка, тип, грамматура, поверхность, цвет, производитель, статус классификации |
| `material_allowed_roles` | допустимые роли слоя |
| `material_external_identifiers` | коды и характеристики 1С и иных источников |
| `material_width_versions` | ширина, статус, период действия, источник |
| `material_price_versions` | цена, единица, валюта, период, источник |
| `material_lots` | партия, поставка, свойства партии |
| `material_rolls` | конкретный рулон, ширина, исходная масса/метраж, статус |
| `unit_conversion_versions` | воспроизводимые правила кг/м/м²/рулон |

Материал со статусом `requires_classification`, `rejected` или `unavailable` не участвует в автоматическом подборе.

## 4. Склад

| Таблица | Назначение |
|---|---|
| `stock_documents` | шапка поступления, списания, корректировки или сторно |
| `stock_movements` | неизменяемые строки движения |
| `inventory_documents` | инвентаризационная сверка |
| `inventory_lines` | учёт, факт, отклонение и стоимость корректировки |
| `writeoff_transactions` | связь списания с заказом, вариантом и snapshot |
| `stock_reservations` | будущий модуль; не используется без утверждённого сценария резервирования |

Уникальный `idempotency_key` действует в пределах организации и типа операции. Проведённое списание исправляется только сторно.

## 5. Импорт

| Таблица | Назначение |
|---|---|
| `import_batches` | тип, UUID, checksum, версия шаблона, автор, исходный файл, статус |
| `import_column_mappings` | подтверждённое сопоставление колонок |
| `import_rows` | исходная строка, нормализованные данные, ошибки и решение |

Повторное подтверждение одной партии не создаёт дубликатов. Файл 1С обрабатывается как обычный источник инвентаризационной сверки и не получает специальных прав.

## 6. Марки, профили и композиции

| Таблица | Назначение |
|---|---|
| `board_grades` | код марки |
| `board_grade_norm_versions` | нормативные ECT и правила сравнения |
| `profiles` | профиль |
| `profile_parameter_versions` | толщина и коэффициенты гофрирования |
| `compositions` | устойчивая карточка композиции |
| `composition_versions` | марка, профиль, статус, период, автор, источник |
| `composition_layers` | порядок, роль, материал или допустимая группа, грамматура, коэффициент |
| `composition_cost_records` | историческая стоимость 1 м² и методика |
| `laboratory_tests` | фактические ECT/BCT и условия испытания |
| `bct_calculation_records` | расчётные BCT и версия метода |

Нормативный ECT, фактический ECT, расчётный BCT и лабораторный BCT — разные типы данных и не записываются в одно поле.

## 7. Оборудование и технологические правила

| Таблица | Назначение |
|---|---|
| `machines` | устойчивая карточка оборудования |
| `machine_parameter_versions` | форматы, панели, клапаны, печать, профили, скорости |
| `corrugator_parameter_versions` | рабочая ширина, ручьи, ярусы, ограничения |
| `trim_rule_versions` | припуск по длине, диапазон, шаг, способ удаления |
| `process_loss_rule_versions` | потери конкретной операции |
| `processing_cost_rate_versions` | тарифы и периоды действия |

Параметр без статуса, источника и периода действия не становится рабочим автоматически.

## 8. Заказ

| Таблица | Назначение |
|---|---|
| `orders` | организация, площадка, клиент, номер, срок, состояние |
| `order_items` | UUID позиции, тип, количество, марка, профиль и исходные размеры |
| `order_item_requirements` | печать, обработка и дополнительные признаки |
| `order_events` | неизменяемая история смены состояний |

Для FEFCO 0201 направление гофры фиксируется по H. Для листовой заготовки направление является обязательным входом до расчёта BCT.

## 9. Расчёт и варианты

| Таблица | Назначение |
|---|---|
| `calculations` | запуск расчёта и его состояние |
| `calculation_snapshots` | полный неизменяемый вход, версии и результаты |
| `layout_variants` | атомарный вариант, допустимость, цена и рейтинг |
| `layout_runs` | один или несколько запусков варианта |
| `layout_lanes` | ручьи, позиция, ярус, длина реза и количества |
| `variant_compositions` | выбранная версия композиции на запуск |
| `variant_material_layers` | конкретный материал, партия/рулон, ширина и цена каждого слоя |
| `material_requirements` | потребность в кг, м, м² и рулонах |
| `layout_selections` | выбранный вариант, пользователь, время, причина |
| `variant_exclusion_reasons` | машиночитаемые причины блокировки |

`algorithm_rank` и `manager_selection` хранятся независимо. Перестановка карточек в UI не меняет исходный рейтинг.

## 10. Отчёты и аудит

| Таблица | Назначение |
|---|---|
| `report_templates` | тип, версия и настройки A4 |
| `reports` | файл, snapshot, вариант, состояние списания |
| `audit_log` | субъект, действие, объект, старое/новое значение и причина |

## 11. Схемная совместимость

- Миграции только последовательные и повторяемые.
- Приложение объявляет минимальную и максимальную поддерживаемую `schema_version`.
- Разрушающая миграция требует периода совместимости и переноса данных.
- Названия таблиц не содержат версии клиентского приложения.
- Клиент не получает прямого доступа к PostgreSQL.
